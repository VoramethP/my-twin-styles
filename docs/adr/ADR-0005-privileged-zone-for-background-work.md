# ADR-0005 — โซนสิทธิ์พิเศษสำหรับงานเบื้องหลัง (webhook · cron · push)

**สถานะ:** ✅ Accepted · 2026-09-19 · แก้ 2026-09-19: ตัวตั้งเวลา = Supabase pg_cron · เพิ่มผู้เรียกที่ 4 (หน้าแชร์)

## บริบท

สแต็กมาตรฐานห้ามใช้ Supabase service role / secret key เพราะมันข้าม RLS ทั้งหมด
แต่การลองเป็นแบบ async (ADR-0001): เมื่อ AI ส่งผลกลับ ไม่มี cookie ของผู้ใช้คนไหนเลย
และระบบยังต้องเก็บรูปลุคลง storage ของผู้ใช้ เก็บงานค้าง/คืนโควต้า และส่ง Web Push (ADR-0004)
งานเหล่านี้ทำในนามผู้ใช้ไม่ได้

## ทางเลือกที่พิจารณา

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| **secret key ในโมดูลเดียว ใช้ได้เฉพาะ 3 จุด** ✔︎ | ฟีเจอร์ครบ (push ตอนปิดแอป) | ถ้าโมดูลนี้รั่ว = ข้าม RLS ทั้งหมด |
| ไม่มี webhook ให้แอปถามสถานะแล้วบันทึกด้วย session ผู้ใช้ | ไม่ต้องมีสิทธิ์พิเศษเลย | ไม่มี push ตอนปิดแอป — ขัดกับ Q18 · ปิดแอปแล้วงานไม่จบ |
| (หน้าแชร์) storage policy เปิดอ่านรูปลุคที่กำลังแชร์ | ไม่ต้องมีผู้เรียกเพิ่ม | ใครรู้ path ก็เปิดได้โดยไม่ต้องมี token — ไม่เลือก (Q31) |
| คิวใน Postgres (Supabase Queues) + worker แยก | รองรับปริมาณมาก | มี worker ให้ดูแลเพิ่ม ยังต้องใช้สิทธิ์พิเศษอยู่ดี |

## การตัดสินใจ

**กลไก:** ใช้ async API ของ provider + webhook และ cron ทุก 1 นาทีเก็บงานค้างเกินเวลา → retry 1 ครั้ง / `refund_quota()`

**ตัวตั้งเวลา:** Supabase `pg_cron` + `pg_net` เรียก `GET /api/cron/try-ons` (migration 0002)
— ไม่ใช้ Vercel Cron เพราะแพ็กเกจ Hobby รันได้วันละครั้ง (Q30) · URL และ `CRON_SECRET` อยู่ใน Supabase Vault ไม่อยู่ใน migration

**สิทธิ์:** secret key ถูกอ่านและสร้าง client ได้ที่ `server/utils/privileged` **ที่เดียว** และเรียกได้จาก 4 จุดนี้เท่านั้น:

| จุด | ต้องผ่านก่อนใช้สิทธิ์ |
|---|---|
| `/api/webhooks/try-on` | ตรวจลายเซ็นของ provider · `provider_job_id` ต้องตรงกับ try_on ที่รออยู่ |
| cron งานค้าง | ตรวจ `CRON_SECRET` จาก header ของ Vercel |
| ส่ง Web Push | เรียกจาก 2 จุดข้างบนเท่านั้น ไม่มี route ของตัวเอง |
| หน้าแชร์ `server/api/share/**` (Q31) | ตรวจ hash ของ token → ลิงก์ยังไม่ถูกเพิกถอน → เซ็นได้**เฉพาะ `looks/<path>` ของลุคนั้น** ทีละรูป อายุสั้น · ห้ามอ่านหรือคืนข้อมูลท่า |

- ทุกการเขียนในโซนนี้ต้องระบุ `user_id` จากแถว `try_ons` ในฐานข้อมูล **ห้ามเชื่อ user_id จาก payload ภายนอก**
- โซนนี้ไม่มีทางอ่านหรือส่งรูปท่าออกไปนอกจาก signed URL อายุสั้นให้ provider (ADR-0003)
- route ที่มี session ผู้ใช้ **ห้าม import** `server/utils/privileged` — ควรมีเทสต์/lint ตรวจ

## ผลที่ตามมา

- secret key อยู่ใน env ของ Vercel เท่านั้น ห้ามอยู่ใน `.env.example` หรือ log
- webhook ต้อง idempotent (provider อาจยิงซ้ำ) — ถ้า try_on จบแล้วให้ตอบ 200 แล้วไม่ทำอะไร
- การตรวจลายเซ็นขึ้นกับ provider ที่เลือก → รายละเอียดอยู่ใน ADR ของการเลือก provider

## ทบทวนเมื่อไหร่

เมื่อปริมาณการลองโตจน cron/webhook รับไม่ไหว (ย้ายไปคิว) หรือเมื่อ Supabase มีวิธีให้สิทธิ์แคบกว่า secret key
